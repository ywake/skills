# penpot-wireframe — Penpot 上に低忠実度ワイヤーを組む

## 概要

Penpot 公式 MCP サーバーの `execute_code`（＝Penpot プラグイン API を JS で実行）を使い、**画面＝ボード** としてワイヤーフレームを Penpot ファイル上に生成し、**クリック遷移をプロトタイプ接続で張る**手法。

**中核原則**: 図形を1個ずつ座標で置かない。**ボード＋フレックスレイアウト**で組む。ワイヤーはレビュー中に何度も作り直すもので、絶対座標で積んだ画面は1要素足すだけで総崩れになる。レイアウトに構造を持たせておけば、中身を差し替えても形が保たれる。

HTML でワイヤーを作る場合は別スキル（`html-wireframe`）の領分。**このスキルは成果物が Penpot ファイル上にあることが要件のとき**に使う（デザイナーが続きを引き取る、Penpot 上でコメントレビューする、PDF にして先方に出す、等）。

**成果物は「1画面＝1台紙ボード」で組む。** 台紙には画面枠・画面ID・注釈レーンを収める。Penpot の PDF 出力はページ内の全ボードを1ボード1ページで束ねる方式なので、**ボードの外に置いた要素は PDF に載らない**。注釈を画面の脇に浮かせて置くと、いちばん伝えたい情報が配布時に丸ごと欠落する。

**扱うのは画面と注釈だけ。** 表紙・凡例・画面一覧・画面遷移図は、このスキルでは作らない。とくに遷移図は、分岐と戻りが増えるとレビューに耐える図を Penpot 上で組むコストが見合わず、図を作る道具（mermaid 等）を持つ別のドキュメントに任せたほうが速い。**そのぶん、各画面の注釈に遷移先を必ず書く**（「押下すると 03 タスク詳細へ遷移する」）。PDF ではプロトタイプ接続が失われるので、注釈だけが紙で流れを追う手がかりになる。

## 前提: MCP 接続とフォーカス

`execute_code` は **ブラウザで開いていて、かつフォーカスされている Penpot ページ** に対してのみ動く。これを外すと「成功したのに何も出てこない」が起きるので、最初に必ず確認する。

1. ユーザーに **対象ファイルをブラウザで開き、目的のページを選択した状態**にしてもらう。同時に MCP を持てるタブは1つだけ。
2. `high_level_overview` を読み、続けて現在地を確認する:
   ```js
   const page = penpot.currentPage;
   return { file: penpot.currentFile?.name, page: page?.name,
            structure: penpotUtils.shapeStructure(page.root, 2) };
   ```
   返ってきたファイル名・ページ名が**ユーザーの意図した場所か**を必ず読み合わせる。ここを飛ばすと他人の作業ファイルを書き換える事故になる。
3. 既存のシェイプがある場合は「消してよいか／横に追加するか」を先に合意する。共同編集中の他人の作業は巻き戻せない。

未接続なら、セットアップは [references/setup.md](references/setup.md) にある。

## 手順

### 1. 画面・遷移・状態を先にテキストで固める

Penpot に手を出す前に、以下をユーザーと合意する。ここが曖昧なまま描くと、作り直しのコストが HTML ワイヤーより高くつく。

- **画面一覧**: 各画面の役割を1行で
- **遷移**: どの画面のどの要素から、どの画面へ
- **状態バリエーション**: 空 / 読込中 / 失敗 / 権限なし / 入力エラー
- **デバイス枠**: phone 375×760 / tablet 768×1024 / desktop 1280×800 のどれか

**状態はすべて別ボードに分ける。** HTML ワイヤーなら入力エラーやモーダルは JS で開閉して同一フレーム内に収められるが、Penpot は静的なので同じ手が使えない。エラー・モーダル・展開状態も1ボードずつ起こし、注釈に「実装では同一画面」と書いて誤解を防ぐ。

**モーダル・ドロワーは下地の画面をクローンして重ねる**（`WF.overlay(baseBoard, {...})`）。空のボードに中身だけ置くと「モーダル」に見えず、レビュアーが独立した別画面と誤解する。オーバーレイは前後関係が分かって初めて評価できる。

### 2. 台紙サイズを決める

`WF.doc({ device })` を最初に一度だけ呼ぶ。以降のページはすべて同じ台紙サイズで作られる。ページごとに紙の大きさが変わる資料は読みづらい。

```js
WF.doc({ device: 'desktop' });   // phone / tablet / desktop
```

### 3. キットを storage に載せ、スモークテストを1本流す

`execute_code` には **呼び出しをまたいで生き残る `storage` オブジェクト**がある。[assets/wf-kit.js](assets/wf-kit.js)（デバイス枠つきボード、行/列コンテナ、プレースホルダ、入力欄、注釈、遷移リンク、グリッド配置、再実行用リセット）の中身を最初の1回だけ流して `storage.WF` に載せれば、以後は `const WF = storage.WF;` の1行で使える。毎回ゼロから座標計算を書き起こすと、画面ごとに寸法規約がぶれる。ただし storage は**接続断やタブのリロードで黙って消える**（「長丁場の運用」参照）。

続けて**ボード1枚＋テキスト1個**だけ作り、Penpot 上に出ることを確認する。いきなり全画面を作らない理由は、`execute_code` が途中で例外を投げると**そこまでに作った図形を残したまま**止まるから。何十個も作る本番コードでこれをやると、残骸の掃除から始めることになる。

### 4. 本番コードも storage に置く

画面定義そのものも `storage.build = () => { ... }` の形で置く。修正のたびに全コードを送り直すのではなく、**直した関数だけ再定義して `storage.build()` を呼ぶ**運用にすると、レビューの往復が軽くなる。画面数が多いときは、共通ビルダーを storage に置いたうえで **`execute_code` 1回＝スクリーン1枚**に分割する（タイムアウト時にどこまで作れたか分かる。「長丁場の運用」参照）。

```js
const WF = storage.WF, P = WF.palette;
WF.reset();                              // 前回分を消してから作り直す
WF.doc({ device:'desktop' });            // 台紙サイズを確定

const s01 = WF.screen({ id:'01', name:'タスク一覧', state:'通常' });
const c = WF.shell(s01.frame, { title:'タスク管理', items:NAV, active:'すべてのタスク' }).content;
const btn = WF.button(c, '＋ 新規作成', { w:140, h:40 });
s01.note('「＋ 新規作成」ボタン', '押下すると 04 新規作成（モーダル）を開く'); // 対象名＋挙動
s01.todo('1ページあたりの件数と、ページ送りか無限スクロールか');              // 未確定事項

const s04 = WF.overlay(s01, { id:'04', name:'タスク新規作成' }); // 01 を下地にモーダル
WF.field(s04.panel, 'タスク名', { value:'未入力' });

WF.layoutPages();                        // 行＝画面/列＝状態に配置＋PDFのページ順を揃える
WF.link(btn, s04.sheet);                 // Penpot 上のクリック遷移
return WF.report();
```

**画面の上には何も描かない。** 番号バッジや引き出し線を重ねると、指したい要素そのものを隠したり、画面を横切って中身を分断したりして、肝心のワイヤーが読みにくくなる。注釈は右レーンだけに置き、対象は**画面に見えているラベルで名指しする**（「「＋ 新規作成」ボタン」「一覧の各行」）。プレースホルダには役割名が書いてあるので、それを引けば対応は取れる。

### 5. 冪等に作る（再実行前提）

ワイヤーは必ず直す。**同じコードを2回流したら同じ結果になる**ように書く。ボード名を `WF-01-入力-通常` のように固定プレフィックス＋連番にし、冒頭で `WF.reset()` を呼んでから作り直す。

こうしないと、修正のたびに旧版のボードが隣に増殖し、どれが最新かレビュアーに分からなくなる。ただし **ユーザーが Penpot 上で直接手を入れた**場合、`reset` はその手直しごと消す。手直しがあると分かっている場合は reset を使わず、対象ボードだけ差し替える。

### 6. 書き出して目視検証する

`export_shape` で各ボードを PNG に書き出し、**自分の目で見る**。コードが例外なく通ることと、ワイヤーとして読めることは別問題で、後述の落とし穴はどれも例外を出さずに見た目だけ壊す。

`shapeId` には**ボードの id を渡す**。`'page'` はルートフレーム全体を指し、幅0のため失敗する:

```js
return penpot.currentPage.root.children
  .filter(s => s.name.startsWith('WF-'))
  .map(s => ({ name: s.name, id: s.id }));
```

見るポイント:

- 要素が枠の下からはみ出していないか（コンテナの高さが中身に追随していない）
- 横に間延びした箱がないか（幅指定が効かず親幅いっぱいに伸びている）
- テキストが溢れていないか、プレースホルダの寄せが実物と合っているか
- 画面の並び順が読む順になっているか

直したら 4〜6 を繰り返す。**画像を見ずに「作成しました」と報告しない。**

### 7. PDF に出して確認する

Penpot のファイルメニューから「ページの全ボードを PDF に出力」する（この操作はユーザーの手元で行う）。出力後、**PDF を開いて確認する**。Penpot 自身が「SVG から PDF への変換は 100% の再現を保証しない」と明記しており、Penpot 上で正しくてもここで崩れることがある。

**ページ順は Penpot 上の見た目では確認できない。** PDF は「最前面のボードが1ページ目」、つまり**レイヤー順の逆**にページを並べる。さらに `overlay()` の `clone()` は下地の隣にボードを挿入するため、作成順のままでは順序が二重に崩れる。`WF.layoutPages()` がレイヤー順を反転して両方まとめて解消するので、ページを作り終えたら必ず呼ぶ。

確認するのは:

- ページ数と順序が意図どおりか（画面IDの昇順になっているか）
- 注釈レーンが全ページに載っているか（台紙の外に要素を作っていないか）
- テキストが欠けたり文字化けしていないか

## 長丁場の運用（タイムアウト・接続断・storage の揮発）

画面数が多い案件（30ボード級）では、途中のタイムアウトや接続断にほぼ必ず遭う。以下はすべて実機で起きた。

**タイムアウト＝失敗ではない。** `execute_code` がクライアント側でタイムアウトしても、Penpot 側は最後まで完走していることが多い。タイムアウト後に同じコードを盲目的に再実行すると**ボードが二重にできる**。必ず先にボード一覧で「どこまでできたか」を確認する:

```js
return penpot.currentPage.root.children.filter(s => s.name.startsWith('WF-')).map(s => s.name);
```

**1画面＝1呼び出しに分割する。** 何画面もまとめた長いスクリプトは、タイムアウトしたときどこまで作れたか分からなくなる。画面ビルダー関数とダミーデータは storage に置き、`execute_code` 1回はスクリーン1枚に抑える。呼び出しが短いほど失敗時の状態が知れて、再開が速い。

**storage は揮発する。** タブのリロード・フォーカス喪失からの再接続・プラグイン UI の再読み込みで、storage は黙って空になる（ボードはファイルに保存済みなので消えない）。接続が戻ったらまず `Object.keys(storage)` で生存確認し、消えていればキットを流し直す。

**採番は再開できるようにする。** 接続断のあと続きから作り足すときは `WF.doc({ device, resume: true })`。ページ上の既存ボード名（`WF-01-02-…`）から枝番と配置グループを拾い直すので、採番が 01 に戻って衝突したり、`layoutPages()` が新しいボードしか並べなくなったりしない。

**`export_shape` が返ってこなくなったら、Penpot タブのリロードを頼む。** ボードが数十枚・シェイプが数千個の規模になると、書き出しがタイムアウトし続けることがある。ユーザーに ⌘R でリロードしてもらうと直る（ボードは残る。storage は消えるので流し直す）。これがあるので、**検証の書き出しは最後にまとめてやらず、画面を作るたびに行う**。

**系統的なバグは一括パッチでなく作り直す。** 生成ヘルパの誤りで何十枚も同じ崩れ方をしたとき、置かれた図形を一括ミューテーションで直そうとすると、絶対配置の暗幕や固定幅のパネルまで巻き込んで二次被害が出る。ヘルパを直して `WF.reset()` から再構築するほうが安全で、結局速い。冪等に作ってあれば作り直しは怖くない。

## 画面の型

キットには、繰り返し出てくる形をまとめた高水準ヘルパがある。毎回組み直すと画面ごとに寸法や余白がぶれるので、まずこれで骨格を作り、細部だけ足す。

| ヘルパ | 用途 |
| --- | --- |
| `WF.doc({ device })` | 台紙サイズを確定する。最初に必ず呼ぶ |
| `WF.screen({ id, name, state })` | 画面ページ。`frame`（画面枠）・`note(対象名, 説明)`・`todo(未確定事項)` を返す |
| `WF.layoutPages()` | **行＝画面 / 列＝状態**に並べ、レイヤー順を反転して PDF のページ順を読み順に揃える。最後に必ず呼ぶ |
| `WF.shell(board, { title, items, active })` | デスクトップの共通シェル（トップバー＋サイドナビ＋本体）。`content` を返す |
| `WF.table(parent, { columns, rows })` | 一覧表。列幅は透明な固定幅コンテナで揃える（テキストを直に並べると列が揃わない） |
| `WF.field(parent, label, { value, hint })` | 入力欄（ラベル＋箱＋補助文） |
| `WF.icon(parent, 'settings', { size })` | 共有ライブラリ（Lucide）から線アイコンを置く |
| `WF.overlay(screen, { id, name })` | 画面ページごとクローンし、暗幕＋モーダル板を重ねる。`panel` に中身を足す |

**領域の切れ目は塗りで示す。** コンテナは既定で透明なので、サイドナビのような領域は `bg` を与えないと本文と一体に見え、レビュアーが構造を読み取れない。`WF.shell` は既にナビに薄い塗りを入れてある。

**並べ方に意味を持たせる。** `WF.layoutPages()` は同じ画面の状態を横一列に、別の画面を縦に並べる。こうすると、行が1枚しかない画面がそのまま「正常系しか作っていない画面」として目に飛び込む。縦一列だと状態の対応が見えず、意味のないグリッドだとどの状態がどの画面のものか読めない。

**空のまま置かない。** 「ここにフィルタが入る（未確定）」のような領域は、空の箱ではなくラベルを置く。無地の余白は読み手に何も伝えず、単なる隙間と区別がつかない。

## アイコン

Penpot の**共有ライブラリ**から実体化する。プラグインのサンドボックスは外部への `fetch` をブロックするため、実行時にアイコンを取りに行くことはできない。ライブラリ経由が唯一の現実的な経路。

```js
WF.icon(parent, 'settings', { size: 16 });          // 単体で置く
WF.shell(s.frame, { title: '…', items: [
  ['list', 'すべてのタスク'], ['user', '自分の担当'],  // ['lucide名', 'ラベル']
], active: 'すべてのタスク' });
```

名前は **lucide とまったく同じ**（`settings` / `plus` / `bell` / `chevron-right` …）なので、`html-wireframe` の `lucide:` 指定とそのまま対応する。探すときは [icon-sets.iconify.design](https://icon-sets.iconify.design) の lucide セットを見る。

**事前にライブラリの接続が要る**（初回のみ・Penpot 上での手作業）。手順は [references/setup.md](references/setup.md) にある。接続していないと `WF.icon()` は「ライブラリが接続されていない」で止まる。黙ってアイコンを飛ばすより、足りない前提をその場で知らせたほうが早い。

`instance()` は 24×24 のボードを返し、中身は黒ストローク2pxのパス。`WF.icon()` は取得直後に `detach()` してから寸法と色を変える。コンポーネントのまま子孫に手を入れても反映されないことがあり、ワイヤーでは元コンポーネントへの追従も要らないため。

自前でいじるときは2点に注意（`WF.icon()` は処理済み）。**縮小は子の constraints を `'scale'` にしてから `resize()`**。先に resize すると枠だけ縮み、中身のパスが 24px のままはみ出す。もう1つ、コンポーネントに `base-background` という**黒ストロークの矩形**が入っていることがあり、消さないとアイコンが「黒い箱入り」で描画される。

## 低忠実度の規律

ワイヤーの目的は**構造と流れの合意**であって見た目の提案ではない。Penpot は本物のデザインツールなので、放っておくと色や角丸を作り込みたくなるが、そこに入ると議論が「この青どう？」に逸れて構造の穴が残る。

- 色は `WF.palette` のグレー階調のみ。ブランド色を使わない
- **線アイコンは使う**（`WF.icon(parent, 'settings')`）。ナビやツールバーが「文字だけの箱の列」になると実物とかけ離れ、要素の見分けがつかない
- 写真・イラスト・ロゴは箱＋ラベル（`WF.box(parent, { w:96, h:96, label:'完了アイコン' })`）のまま。中身が未確定なものを絵にすると低忠実度でなくなる
- テキストはダミー文でなく**役割名**を書く（「見出し」「商品名」「未入力」）。Lorem ipsum は要素の意味を隠す
- 影・グラデーション・カスタムフォントを使わない

決まった項目だけ、注釈に「確定: 〜」と明記する。

## レイアウトの落とし穴（実機で踏んだもの）

以下はいずれも**例外を出さずに見た目だけ壊れる**ため、書き出し画像を見るまで気づけない。`WF.place()` / `WF.text()` が大半を吸収しているので、キット経由なら踏まない。自前でヘルパを書くときは要注意。

| 挙動 | 症状 | 対処 |
| --- | --- | --- |
| `resize()` は `layoutChild` の sizing を `'fix'` に戻す | `horizontalSizing='fill'` を指定したのに親幅に広がらない | **resize → sizing の順**で設定する（Text の `growType` と同じ挙動） |
| 寸法未指定のまま `'fix'` | 既定 100px で固定され、中身が枠から溢れる | 高さを決めないコンテナは `verticalSizing='auto'`（中身なり） |
| sizing を一律 `'fill'` にする | 96×96 のアイコン枠が横一杯に伸びる | 幅を決めた要素は `horizontalSizing='fix'` |
| 高さを決めた要素に `verticalSizing='fill'` | ボタンや入力欄が兄弟と親の高さを分け合い、0px に潰れる／画面いっぱいに間延びする | 高さ指定した要素は縦 `'fix'`。「親幅いっぱい」は横 `'fill'` だけで表す。`place()` の `grow` は**縦 fill** なので横伸ばしのつもりで渡さない |
| `'auto'` を**子を入れる前**に指定 | 既定 100px のまま焼き付き、子を足しても再計算されない | `WF.hug()` で印を付けて組み、最後に `WF.settle(sheet)` を呼ぶ（`'fix'`→`'auto'` と設定し直すと再計算が走る） |
| 高さ固定の行に同値の縦パディング | 内側の余地（h − padding×2）が消え、アイコンやテキストが黙って切れる | 高さ固定＋`align:'center'` の行に縦パディングは付けない。余白は横だけにする |
| テキストは折り返さない | 注釈レーンの長文が枠を突き抜けて切れる | `WF.text(..., { wrap: true })`（`growType='auto-height'`＋横 `'fill'`＋親 `alignItems:'stretch'`） |

その他の型の落とし穴（`fontSize` が文字列、`createText` が null を返しうる 等）は [references/plugin-api.md](references/plugin-api.md) にまとめてある。

## API の細部は推測しない

確信が持てないプロパティ名・値は、書く前に **`penpot_api_info` ツールで確認する**。うろ覚えで書くと、例外にならず「指定が無視される」形で失敗する。シェイプ探索は自前で書かず `penpotUtils`（`findShape` / `findShapes` / `shapeStructure` / `setParentXY`）を使う。

## よくある失敗

| 失敗 | 直し方 |
| --- | --- |
| 何も表示されない | 対象タブがフォーカスされていない／別ページを見ている。`penpot.currentPage` で現在地を確認 |
| 図形を絶対座標で1個ずつ配置 | `WF.row` / `WF.col`（＝フレックスレイアウト）で組む。要素追加で崩れなくなる |
| 修正のたびにボードが増殖 | 固定プレフィックス命名＋`WF.reset()` で冪等に |
| 例外で中途半端な図形が残る | スモークテスト先行。失敗したら `WF.reset()` で掃除してから再実行 |
| 要素が枠からはみ出す／横に間延びする | レイアウトの落とし穴の表を参照。キット経由でサイズを決める |
| `export_shape` が失敗する | `shapeId:'page'` ではなくボードの id を渡す |
| 正常系の画面だけ作る | 状態を先に列挙し、Penpot では**すべて別ボード**に起こす |
| 遷移が Penpot 上に無く、口頭説明だけ | `WF.link()` でプロトタイプ接続を張る。触れないと流れは検証できない |
| PDF にすると遷移が分からなくなる | 各画面の注釈に遷移先を書く。プロトタイプ接続は紙では失われるので、注釈だけが手がかりになる |
| 遷移図をこのスキルで描こうとする | 分岐と戻りが増えると Penpot 上で組むコストが見合わない。図は別ドキュメントに任せる |
| アイコンが出ない／`WF.icon` で止まる | Lucide のライブラリが未接続。Penpot Hub から取り込んで共有ライブラリ化し、ファイルに接続する |
| アイコンが黒い箱をまとう／縮めても中身が大きいまま | `WF.icon()` を経由する（`base-background` の除去と constraints→resize の順を処理済み）。絵文字・記号での代用はカラー絵文字になり灰色の規律から外れる |
| タイムアウト後の再実行でボードが二重になる | タイムアウト≠失敗。先にボード一覧で状態を確認してから再開する（「長丁場の運用」参照） |
| 接続断のあと `storage.WF` が undefined | storage は揮発する。`Object.keys(storage)` で生存確認→キットを流し直し、`WF.doc({ resume: true })` で採番を復元 |
| 生成ヘルパのバグを置かれた図形への一括パッチで直す | 暗幕や固定幅パネルを巻き込んで二次被害が出る。ヘルパを直して `WF.reset()` から再構築する |
| ナビやツールバーが文字だけの箱の列になる | `WF.shell` の items を `['lucide名', 'ラベル']` にする。実物との差が大きいと要素の見分けがつかない |
| 色や角丸を作り込む | グレー階調に戻す。低忠実度の規律を参照 |
| モーダルを単独ボードで作る | `WF.overlay()` で下地をクローンして重ねる。前後関係がないと評価できない |
| サイドナビ等の領域が本文と一体に見える | コンテナに `bg` を与える。既定は透明 |
| 生成物の命名が `WF-` 始まりでない | `reset()` が拾えず残骸になる（注釈も `WF-note:…` にしてある） |
| 注釈が PDF に載らない | 台紙ボードの外に要素を作っている。`WF.screen()` の `note()` / `todo()` を使う |
| 注釈のために画面の上に何かを描く | 番号も引き出し線も置かない。右レーンで対象をラベル名で名指しする |
| ページ順が PDF と食い違う | `WF.layoutPages()` を最後に呼ぶ。PDF 順はレイヤー順で決まり、キャンバス上の位置とは無関係 |
| ユーザーの手直しを reset で消す | 手直しがある場合は reset せず対象ボードだけ差し替える |
