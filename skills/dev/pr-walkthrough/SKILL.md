# pr-walkthrough — PR を会話しながら段階を追って見る

レビュー担当者（ユーザー）が1つの PR を見るのを案内する。出す情報を段階ごとに絞り、レビュー担当者が一度に抱える量を小さく保つ。判断するのはレビュー担当者で、指摘や質問は最後にまとめて PR へのレビューとして出す。

`/pr-walkthrough <PR の番号か URL>` で呼ぶ。対象の PR があるリポジトリの中で使う。PR の番号か URL が示されていなければ聞く。

## 考え方

diff には、実装者の答えである行だけがパス順に並ぶ。目的、機能、設計を行から逆算し終えるまで、読み手は何も判断できず、読んだ行を頭に溜めることになる。逆算が終わるころには実装者の設計が頭に入っていて、自分ならどうするかを切り離して考えられない。

そこで、次のように出す。

- **判断できる順に出す。** 目的、機能、設計、構造、細部の順。どの段階も、1つ上の段階に照らして判断する。
- **答えの前に問題を渡す。** レビュー担当者が自分の案を言うまで、実装者の設計を出さない。レビュー担当者の物差しを、実装者の設計を見る前に作るためである。
- **予想できる部分は畳み、予想から外れる部分を出す。** 絞る基準は、レビュー担当者の案と、レビュー担当者が納得した設計に置く。
- **畳んでも隠さない。** 畳んだものは理由と件数を一覧で出し、頼まれたら開く。
- **確かなことと推測を分ける。**
- **材料が先、意見は後。** 決めるのはレビュー担当者。

## 発言の形

1回の発言は、次の3つをこの順で書く。

1. いまの段階。例: `目的（1/6）`
2. その段階の「出すもの」
3. レビュー担当者に求める判断を1つ

発言に入れるのは、いまの段階の「出すもの」だけにする。PR 全体を読んで気づいたことは、それを出す段階が来たときに出す。

1回の発言は短く保つ。箇条書きは7項目まで、1項目は2行までにする。収まらないときは、まとまりごとの見出しと件数にして、細かい項目は頼まれたら開く。

レビュー担当者の返事を待って、次の段階に進む。レビュー担当者は、前の段階に戻れる。段階を飛ばすのは、レビュー担当者が飛ばすと言ったときだけにする。レビュー担当者に聞かれたことには、段階に関係なく答える。

内容には、確かさの印を付ける。

| 印 | 意味 |
| --- | --- |
| 書かれている | issue、PR の説明、コミットに書かれている。出どころを添える |
| 推測 | AI が diff やコードから推測した |
| 確認済み | コマンドで機械的に確かめた。コマンドを添える |
| 読んだ判断 | AI がコードを読んで、そう判断した |

## 準備

最初の発言の前に、PR 全体を読む。`<置き場>` は `${TMPDIR:-/tmp}/pr-walkthrough/<owner>-<repo>-<番号>/` で、作業ツリーの外にある。

```sh
# 置き場を作る。PR ごとに同じ場所になるので、会話が長くなっても見失わない
mkdir -p <置き場>

# PR の概要、紐づく issue の番号、コミットを読む
gh pr view <番号> --json number,title,body,author,state,isDraft,baseRefName,headRefOid,additions,deletions,changedFiles,closingIssuesReferences,commits,url

# 紐づく issue を読む。目的の出どころになる
gh issue view <issue番号> --comments

# diff を置き場に保存して読む。大きい diff は分けて読む
gh pr diff <番号> > <置き場>/pr.diff

# 変更されたファイルの状態と増減を一覧する。PR の大きさと、構造の段階の一覧に使う
gh api "repos/{owner}/{repo}/pulls/<番号>/files" --paginate \
  --jq '.[] | "\(.status)\t+\(.additions)/-\(.deletions)\t\(.filename)"'

# PR の先頭のコードを、ブランチを切り替えずに読めるようにする
git fetch origin pull/<番号>/head
git show <headRefOid>:<パス>               # ファイルを読む
git grep -n '<語>' <headRefOid> -- <パス>   # 呼び出し側などを探す
```

`origin` が PR のあるリポジトリを指していないときは、指しているリモート名に置き換える。レビュー担当者の作業ツリーは変えない（ブランチの切り替え、ファイルの編集をしない）。

## 段階

| 順 | 段階 | 出すもの | 何に照らして判断するか |
| --- | --- | --- | --- |
| 1 | 目的 | この PR は何のためにあるか | レビュー担当者が知っているプロジェクトの事情 |
| 2 | 機能 | 何ができるようになるか、何が変わるか | 目的 |
| 3 | 自分の案 | レビュー担当者への問い | — |
| 4 | 設計 | 実装者がどういう考えで解いたか | 目的、機能、自分の案 |
| 5 | 構造 | どんなファイル、クラス、関数に分けたか | 設計 |
| 6 | 細部 | 行 | 設計、構造 |

レビュー担当者が差し戻すと決めたら、残りの段階を飛ばして「コメントを出す」に進む。

### 1. 目的

- 出すもの: 書かれている目的を、出どころを添えて出す。目的は diff の外から持ってくる。どこにも書かれていなければ「書かれていない」と伝え、AI の推測を「推測」として出す。diff から推測した目的は実装と必ず合うので、レビュー担当者が認めるまでは、設計を判断する物差しにならない。レビュー担当者が認めたもの、または言い直したものを、以降の段階の目的にする。あわせて、PR の大きさ（ファイル数と行数）を1行で伝える。
- 求める判断: この目的の PR として見ていってよいか。

### 2. 機能

- 出すもの: この PR で何ができるようになるか、何が変わるか。使う人や呼び出す側から見える言葉で書く。
  - 目的から予想できる機能は、まとまりごとに1行で書き、細かい項目の件数を添える。
  - 目的に書かれていない機能は、畳まずに1つずつ書く。7項目を超えるときは、発言を分けて出す。
- 求める判断: 目的に対して、機能に過不足がないか。

### 3. 自分の案

- 出すもの: 問いを1つだけ。「この目的と機能を、あなたならどう作りますか。一言で構いません」
- 案が思い浮かばないと言われたら、4 で設計と主な決めごとをそのまま出す。

### 4. 設計

最初の発言で、全体を出す。

- 実装者の方針を2〜3行。
- レビュー担当者の案と同じところは、「同じ」とだけ伝える。
- 違うところの件数と見出し。

続く発言で、違うところを1つずつ出す。1つの発言は次の順で書く。

1. 両方のメリデメ。物差しは目的と機能。レビュー担当者の案は、実際のコードに当てて確かめる。例: 「その案だと、既存のこの呼び出し側をすべて変えることになる」
2. 実装者が選んだ理由。PR やコミットに書かれていれば、出どころを添えてそのまま示す。書かれていなければ「推測」として出す。
3. AI の意見。「意見」と断り、理由を添える。

- 求める判断: この違いは、このままでよいか、直してほしいか、実装者に聞きたいか。

### 5. 構造

- 出すもの: 追加、変更、削除されたファイル、クラス、関数の一覧。それぞれに役割を1行と、呼び出しの関係を添える。中身の行は出さない。数が多いときは、役割ごとにまとめる。
- 求める判断: この分け方でよいか。

### 6. 細部

最初の発言で、行の分け方を出す。

- 見せる箇所の一覧。5 で確認した関数やクラスごとに、見せる理由を添える。
- 畳む箇所の一覧。種類ごとに、件数と確かさの印を添える。
- 求める判断: この分け方で進めてよいか。開きたい箇所はあるか。

diff のすべてのハンクを、見せる箇所か畳む箇所のどちらかに入れる。ハンクの一部だけを見せるときは、残りの行をどの畳む箇所に入れたかを添える。どちらにも入らないハンクが残っていないことを、ハンクの数（`grep -c '^@@' <置き場>/pr.diff`）と突き合わせて確かめてから出す。

続く発言で、見せる箇所を1つずつ出す。パスと行番号、diff の該当部分、見せる理由を書く。

- 求める判断: 問題ないか、コメントするか。

見せる理由は次の3つ。

- **予想外**: 納得した設計から予想できない行。目的にも設計にも出てこなかった変更など。
- **重要**: 予想どおりでも見せる行。
  - 取り消せない操作（データの削除や上書き、DB のマイグレーション）
  - 権限の判定
  - お金や数量の計算など重要なところ
  - 秘密の扱い
  - テストを弱める変更（既存テストの削除、スキップ、期待値の書き換え）
  - 設定と依存。依存の追加や更新は、依存を宣言するファイル（`package.json` など）の行を見せる。lockfile は、機械的な変更として畳む。
- **読んだ判断**: 準備で読んでいて、AI が怪しいと判断した行。問題を探すための専用の読み込みはしない。

畳む行は、次の3種類に分けて出す。

- **繰り返し**: 納得した設計から予想できて、同じ規則の繰り返しになっている行。規則、件数、例を1つ添える。規則に合わない箇所は、見せる箇所に入れる。
- **設計どおり**: 設計と構造の段階で確認した内容を、そのまま書いた行。5 で確認した単位ごとに、箇所の数を添える。確かさは「読んだ判断」になる。
- **機械的な変更**: 生成物（lockfile、スナップショット、自動生成コード）と、中身の変わらない移動や改名。ファイル名と行数を添える。

## コメント

レビュー担当者が「直してほしい」「実装者に聞きたい」と言ったら、理由を添えたコメントの文を書き、`<置き場>/review.json` に足す。diff に含まれる行への指摘は `comments` に、それ以外は `body` に入れる。足したことを、件数と1行の要約で伝える。AI が気づいた問題をコメントにするかどうかも、レビュー担当者が決める。

```json
{
  "commit_id": "<headRefOid>",
  "event": "COMMENT",
  "body": "PR 全体や設計へのコメント。なければ空文字",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "side": "RIGHT", "body": "行へのコメント" }
  ]
}
```

- `line` は PR の先頭のファイルでの行番号で、diff に含まれる行に限る。diff に含まれない行が1つでもあると、レビュー全体が `Line could not be resolved` で断られる。範囲に付けるときは、開始行の `start_line` と `start_side` を足す。
- 削除された行に付けるときは、`side` を `LEFT` にし、変更前のファイルでの行番号を使う。
- diff に含まれない行への指摘は、パスと行を書いて `body` に入れる。
- 行を持たないコメント（目的や設計への指摘、差し戻しの理由）も、`body` に入れる。

### コメントを出す

最後の箇所を見終えたとき、またはレビュー担当者が差し戻すと決めたときに出す。

1. 溜めたコメントの全文を一覧で見せ、Approve、修正依頼、コメントのみのどれで出すかを聞く。文面の直しがあれば、ここで受ける。レビュー担当者が PR の作者のときは、コメントのみで出すと伝える。
2. `gh pr view <番号> --json headRefOid` で、PR の先頭が準備のときから変わっていないことを確かめる。変わっていたら、レビュー担当者に伝える。
3. `event` を `APPROVE`、`REQUEST_CHANGES`、`COMMENT` のどれかにして送る。

   ```sh
   # 溜めたコメントを、1つのレビューとして送る
   gh api "repos/{owner}/{repo}/pulls/<番号>/reviews" --method POST \
     --input <置き場>/review.json --jq '.html_url'
   ```

4. 返ってきた URL を伝える。

`COMMENT` は、行へのコメントが1件もなく `body` も空だと送れない。`REQUEST_CHANGES` を送るときは `body` を書く。PR の作者が自分の PR に `APPROVE` か `REQUEST_CHANGES` を送ると、GitHub が断る。

## 発言の例

最初の発言。

```markdown
**目的（1/6）**

- 書かれている: 注文一覧の表示を速くする（issue #120）
- 書かれている: 一覧 API の N+1 をなくす（PR の説明）

大きさは 34 ファイル、+1,820/−640 です。

この目的の PR として見ていってよいですか？
```

細部の最初の発言。

```markdown
**細部（6/6）**

見せる箇所は4つです。

1. `OrderRepository.deleteExpired`: 重要（取り消せない操作）
2. `canViewInvoice`: 重要（権限の判定）
3. `.github/workflows/ci.yml`: 予想外（設計に出てこなかった変更）
4. `PriceCalculator.round`: 読んだ判断（端数の扱いが既存の計算と違う）

畳む箇所は4つです。

- 繰り返し: `getUser` から `fetchUser` への改名。27 ファイル、61 箇所。例: `api/users.ts:14`。確認済み（`git grep -c 'getUser(' <headRefOid>` が 0 件）
- 設計どおり: `OrderQuery`（一覧をまとめて取る問い合わせ）。4 箇所。読んだ判断
- 設計どおり: `OrderListController`（`OrderQuery` を呼ぶように変更）。2 箇所。読んだ判断
- 機械的な変更: `package-lock.json`。312 行

この分け方で進めてよいですか？ 開きたい箇所があれば言ってください。
```
