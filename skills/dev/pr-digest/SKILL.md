# pr-digest — レビュー前に PR を読み解いたレポートを作る

## 概要

PR の diff はファイル順に並んでいて、意図の単位になっていない。レビュアーは「どこから読むか」「この変更の周辺はどうなっているか」「なぜこうしたのか」を毎回自分で組み立て直している。このスキルはその組み立てを先に済ませ、**レポートだけで判断を終えられる**状態にする。

**中核原則**:

- **説明ではなく判断の材料を出す**。読む順番と確認点をレポートの先頭に置く。
- **リポジトリを開かせない**。本質的な変更の hunk は省略せず載せ、周辺コードは該当行を引用する。
- **付随的な変更を本質から隔離する**。rename・整形・生成物は一覧に落とし、diff を載せない。

レポートは材料であり、approve / request changes の判断は人がする。

## いつ使うか

- PR の URL や番号を渡されて「レビューして」「読んで」「説明して」「まとめて」と言われたとき
- 自分のブランチの PR を出す前に、レビュアー視点で読み直したいとき

**使わない**:

- 自分の作業ブランチの未コミット差分の整理（それは `git-commit` の領分）

## 成果物

| 出力先 | 条件 | 場所 |
| --- | --- | --- |
| Markdown ファイル | cwd が対象リポジトリの clone の中 | `<repo-root>/PR-<num>.md`。`.git/info/exclude` に登録して誤コミットを防ぐ |
| PR コメント | それ以外 | `gh pr comment <num> --body-file <file>` で投稿 |

雛形は [templates/report.md](templates/report.md)。構造を変えずに埋める。

## 手順

1. **PR を特定する**。引数の URL / 番号を使う。無ければ `gh pr view --json number,url` で現在ブランチの PR を取る。
2. **出力先を決める**。`gh repo view --json nameWithOwner` が PR の `owner/repo` と一致すればローカルあり。一致しない、または cwd が git リポジトリでなければ scratch に clone する:

   ```sh
   gh repo clone OWNER/REPO "$SCRATCH/REPO" -- --filter=blob:none   # blob は必要時に取る。巨大リポジトリでも速い
   ```

3. **材料を集める**。PR 本文・commit・diff・リンク先 issue を取り、PR head を参照として持ってくる。**ユーザーの clone では checkout しない**（作業ツリーを動かさない）:

   ```sh
   gh pr view NUM --json title,body,baseRefName,headRefOid,commits,files,additions,deletions   # headRefOid はパーマリンクに使う
   gh pr diff NUM                                    # 全 diff
   gh pr diff NUM --name-only
   gh issue view ISSUE                               # 本文に "closes #N" 等があれば
   BASE=$(gh pr view NUM --json baseRefName -q .baseRefName)
   git fetch origin "pull/NUM/head:refs/pr/NUM" "$BASE"   # PR head と base を参照として取得。branch は作らない
   ```

4. **付随的な変更を除ける**。「付随的な変更の判定」に従い、先に隔離して一覧化する。残りが本質的な変更。
5. **本質的な変更を関心に分解する**。「関心の切り方」に従い、中核 → 波及の順に並べる。
6. **各関心の周辺を読む**。「周辺の読み方」に従い、判断に要る行を `path:line` 付きで引用する。作業ツリーではなく参照から読む:

   ```sh
   git grep -n 'symbol' "origin/$BASE" -- '*.ts'    # 変更前のコードを検索
   git grep -n 'symbol' refs/pr/NUM -- '*.ts'       # 変更後のコードを検索
   git show "refs/pr/NUM:path/to/file" | sed -n '10,40p'   # 変更後のファイルの一部を読む
   ```

7. **意図を復元する**。「意図の復元」に従う。
8. **確認点を抽出する**。「確認点の書き方」に従う。
9. **書く**。雛形を埋める。hunk は `gh pr diff` の出力を scratch に保存し、行範囲を指定してスクリプトで切り出す（手で写すと落ちる・ずれる）。図は「図を使う条件」を満たすときだけ。書き終えたら「出す前の自己点検」を通す。
10. **出す**。ローカルありなら `<repo-root>/PR-NUM.md` に書き、`echo 'PR-*.md' >> .git/info/exclude`（未登録なら）してパスを伝える。ローカルなしなら `gh pr comment NUM --body-file` で投稿し URL を伝える。

## 関心の切り方

- 1 関心 = **1 つの理由で説明できる変更のまとまり**。ファイル単位ではない。1 ファイルが複数の関心にまたがることも、1 関心が 10 ファイルに散ることもある。
- 並べる順: **中核**（PR の目的そのものを実現する変更）→ **波及**（中核に合わせて変えざるを得なかった呼び出し元・型・テスト）。付随的な変更は別節に隔離する。
- 目安は 2〜6 個。10 を超えるなら切り方が細かすぎるか PR が大きすぎる。後者は概要に「分割を提案」と書く。
- 同じ hunk を複数の関心に載せない。またがる場合は主たる関心に載せ、他方から「§N 参照」と書く。

## 付随的な変更の判定

以下は diff を載せず「付随的な変更」節に 1 行ずつ書く:

- rename / move のみ（`git diff -M` で類似度 90% 以上、中身の変更なし）
- import 整理・フォーマット・lint 修正のみ
- 生成物（lockfile・snapshot・build 出力・自動生成コード）
- コメント・ドキュメントの誤字修正

迷ったら本質側に入れる。隔離しすぎて見落とす方が高くつく。rename に中身の変更が混ざっている場合は、rename を付随に、中身の変更を本質に分けて書く。

## 周辺の読み方

各関心について:

- 変更されたシンボル（関数・型・定数・設定キー）の**呼び出し元を列挙**し、呼び出し元の前提（null を渡すか、呼び出し順に依存するか、例外を期待するか）を確認する。
- **変更前の実装を読み**、追加された振る舞いだけでなく**削除された振る舞い**を押さえる。
- 引用は判断に要る行だけ。ファイル丸ごとは載せない。引用には `path:line` をパーマリンクにして添える: `[src/save.ts:40-44](https://github.com/OWNER/REPO/blob/HEAD_SHA/src/save.ts#L40-L44)`。変更後は `headRefOid`、変更前は `git rev-parse origin/$BASE` の SHA を使う。
- テストの diff があれば「何がテストされ、何がテストされていないか」を読む。テストが無い分岐は確認点の候補。

## 意図の復元

優先順: **PR 本文 → リンク先 issue → commit メッセージ → コードからの推測**。

- 推測で補った部分は文頭に「推測:」を付ける。
- PR 本文と実装が食い違う場合は、それ自体を確認点にする。
- 「なぜこのアプローチか」が書かれていなければ、コードから読み取れる範囲で書き、他に取りうる方法があれば確認点で触れる。

## 確認点の書き方

- 「〇〇の場合に △△ にならないか」の形にし、根拠（引用した周辺コード、テストの不在）を添える。
- 断定しない。「バグ」「間違い」ではなく「確認してほしい」。PR コメントに出すときは作者への質問形にする。
- 各確認点に対応する節（§N）を付け、詳細側の「気になる点」と対応させる。
- 見つからなければ「特になし」と書く。無理に作らない。

## 図を使う条件

行 diff で構造が読めないときだけ。**Before / After** を縦に並べる。種類ごとの見本（印の付け方を含む）は [references/figures.md](references/figures.md)。

| 変更の種類 | 図 |
| --- | --- |
| 処理フローの組み替え | `flowchart` / `sequenceDiagram` |
| 状態遷移の追加・削除 | `stateDiagram-v2` |
| 依存関係・呼び出し関係の変化 | `flowchart`（ノードは関数 / モジュール） |
| スキーマ・型構造の変更 | `erDiagram` または表 |

図は**変わった区間だけ**切り出す。全体図を 2 枚並べると見比べる負荷が diff より高い。シーケンス図なら、変わらない前後の手順は `Note over` 1 行に畳み、抜粋に登場しない participant は消し、同じ役割の相手（DI と LLM など）は 1 つに畳む。ER 図・状態遷移図は変わったエンティティ・状態だけ。行 diff で十分読めるなら図は載せない。

**mermaid など図のソースを変える hunk は diff に載せない**。ソースの行差分は絵として読めないので、mermaid 部分を hunk から外し、base と head から図を取り出して Before / After で並べる（`git show origin/$BASE:path` と `git show refs/pr/NUM:path` から ```` ```mermaid ```` ブロックを抜く）。追加だけなら After だけ。participant の削除や文言だけの変更は図を載せず付随に回す。

**目印**（After で「どこが変わったか」を示す。「詳細」の冒頭に凡例を 1 行置く）:

- 印はラベルの先頭に置く。追加 `🆕`、変更（名前・意味・条件が変わった）`✏️` は After 側、削除 `⛔` は Before 側。1 要素に印は 1 つ。地味な記号（＋ ～ −）や灰色の絵文字（🗑️ ➖）は目に入らないので使わない。✅ ❌ は「承認」「誤り」に読まれるので使わない。
- 色は**順序や構造が組み替わった区間**に付ける。シーケンス図は `rect rgba(255, 193, 7, 0.18)` で囲む。状態遷移図・flowchart のノードは `classDef changed fill:#ffc10733,stroke:#ffc107,stroke-width:2px` を宣言して `class X changed`、flowchart の辺は `linkStyle N stroke:#ffc107,stroke-width:2px`。透過にするのはライト／ダーク両テーマで読めるようにするためで、文字色は指定しない（テーマに任せる）。classDef はカンマ区切りなので rgba は使えず 8 桁 hex にする。
- `rect` 自体にはラベルを付けられないので、塗った区間の先頭に `Note over` を 1 行置いてキャプションにし、`🆕`（区間ごと新規）／`🔀`（順序・構造の組み替え）／`⛔`（Before 側の消える区間）を付ける。塗った区間の中で全行が新規なら各行に印は付けない。塗ったノードから出る辺にも付けない（色が示す）。1 図あたり色は 2 区間まで。
- ER 図は印だけ（erDiagram の style は描画環境で効かないことがある）。**列はセル単位**で示す: 説明セルに元の説明を残し、`<br/>` で改行してから `✏️名 旧→新`（名前）、`✏️型 旧→新`（型）、`✏️意 旧→新`（nullable・制約・意味）を必要なだけ並べる。新規列は `<br/>🆕`、消える列は Before 側に `<br/>⛔ 移動先や理由`。型と名前のセルには mermaid の制約で ASCII 識別子しか置けないため、印はすべて説明セルに書く。エンティティの改名も同じ書き方で角括弧のラベルに。全列が新規のエンティティはラベルにだけ `🆕` を付け、列には付けない。`<br/>` は mermaid 11.4 以降の ER 描画で改行になる。古い描画環境では文字のまま出るので、投稿前にプレビューで確認する。
- 図全体が新規なら印を付けず「新規」と書く。
- 凡例の文言: `凡例: 背景色＝順序や構造が変わった区間（先頭の Note に 🆕 新規区間／🔀 組み替え／⛔ 消える区間）、🆕＝追加、✏️＝変更（After 側）、⛔＝削除（Before 側）。ER 図の列は元の説明の下に ✏️名・✏️型・✏️意（名前・型・意味のどれが変わったか）と旧→新を書く。`

## 出す前の自己点検

- 本質的な変更の hunk が**すべて**レポートに載っているか。「以下同様」「...」で端折っていないか。diff の全行番号から「載せた範囲」「図で置き換えた範囲」「付随に回した範囲」を引いて残りが空になることを機械的に確かめる。
- **Markdown の diff は 4 バッククォート（````diff）で囲む**。diff の中の ` ```mermaid` は先頭がスペース 1 つの文脈行になり、3 バッククォートの外側フェンスを閉じてしまう。
- 「読む順番と確認点」が参照する §N が詳細に存在するか。
- 推測に「推測:」が付いているか。
- 各確認点に根拠があるか。
- PR コメントに出すときは、パーマリンクを**単独行に裸で**置くと GitHub がスニペットに展開する。周辺の引用はコードブロックの代わりにこれで済ませてよい（文字数も減る）。
- PR コメントは 65,536 文字が上限。超える場合は「概要＋読む順番と確認点」を 1 コメント目に、関心ごとに続けて投稿する。
- レポートの言語は日本語。コード・識別子・引用はそのまま。
